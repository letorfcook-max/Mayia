# Release process
1. Run `npm install`, `npm run check`, `npm run build` on the intended OS. For real native packaging run `npm run dist:win` or `npm run dist:mac`; run `npm run dist` on Linux.
2. Keep the old `mayia` tag for legacy installers. Upload the V2 source files on a new branch and test the CI workflow. Set a semantic package version and matching Git tag, e.g. `v2.0.0`. Don't overwrite a previous release.
3. Native tests: clean install, launch, chat with configured provider, permissions, save data, quit, reinstall, update from a lower semantic version, verify data, uninstall; repeat on Windows x64, macOS x64/arm64, and Linux target. Test a denied file operation and an interrupted update download.
4. Sign Windows installer using a trusted code-signing certificate; on macOS configure Developer ID Application signing and Apple notarization via electron-builder's supported credentials. The CI defaults to unsigned test artifacts and must be configured with secure repository secrets for signing. Never commit credentials. Verify platform signatures after signing. Signed packages have to be tested again.
5. Publish native installers named `Mayia-2.0.0-win-x64.exe`, `Mayia-2.0.0-mac-arm64.dmg` etc. from the actual build output; ensure names include `x64` or `arm64`. GitHub must report the `sha256:` digest on assets for verified download. Keep release notes truthful. Release workflow is artifact-only; publish after validation. Update checks require stable semantic tags, not the mutable `mayia` release. A future verified native automatic updater can be added after signing and platform regression tests.
